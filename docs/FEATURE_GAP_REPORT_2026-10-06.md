# ELOVERIS 功能补充与实现技术路线报告

报告日期：2026-10-06（北京时间） 
审查对象：当前工作区 ELOVERIS 0.2.1，Git HEAD `7304df4`
面向读者：产品、前端、后端与算法开发人员

## 1. 结论与审查边界

软件已经具备“输入英文稿件 → 生成示范 → 单句录音 → 回听 → 转写与评测”的基础流程。下一阶段建议优先补齐**可靠保存和任务恢复、稿件与数据管理、整篇连续练习**，然后增加**无稿回答、语言复盘和弱项复练**。模型数量已经较多，继续增加模型不是目前最主要的功能缺口。

本报告依据当前源码、API、前端交互和仓库验收文档编写；外部技术资料于报告日核查。没有重新运行应用、真人录音、模型推理、自动测试或付费 API，因此：

- “已实现”表示当前源码存在对应业务路径，不表示本轮重新验收通过。
- “缺失”表示在所检查的界面、接口及数据结构中没有发现完整实现。
- “部分实现”表示已有数据或基础能力，但缺少用户可以完成的流程。
- “待验证”表示实现已存在，效果、兼容性或运行稳定性仍缺证据。
- 优先级、验收标准和开发顺序均为本报告的建议，不是已有产品承诺。

与 [2026-10-04 规划报告](./ITERATION_TECHNICAL_REPORT_2026-10-04.md)相比，当前代码已经接入更大的 Whisper 模型、GPU ASR、腾讯云适配、反馈时间轴、Parakeet 和 Qwen 0.6B。这些应从“待开发功能”改为“已有实现、继续验收或完善”，避免重复立项。

## 4. 各功能的技术路线与验收方法

### F01：录音草稿恢复与正确版本归属

**缺口。** 当前 `MediaRecorder.start(250)` 已定期产生片段，但片段只进入前端内存中的 `chunks`，停止后才上传。上传失败时已有临时回听/下载，这是有用的保护；尚未发现持久草稿和失败重传接口。前端录音前保存稿件，但上传请求只传句子 ID，后端在上传开始时读取稿件快照，因此多窗口/API 并发修改下，仍需验证录音开始时的版本归属。

**路线。**

1. 新增 `recording_draft` 和 `POST /api/recording-drafts`：开始录音时由后端返回草稿 ID，并固化句子 ID、版本、朗读稿、练习模式和开始时间。
2. 经受限 Electron IPC，按序号追加编码片段到应用数据目录；使用草稿 ID 定位路径，不接受渲染进程任意文件路径。队列设置背压和空间上限。
3. 停止后按序拼接原始容器数据，再解码为 WAV。片段不保证都能独立解码；不要将每个 Blob 当作独立音频文件转换。
4. 保存完成后原子标记 finalized；失败保留草稿，提供重传、下载与丢弃入口。重复提交由草稿 ID 去重。
5. 启动时扫描未完成草稿；不可完整解码的尾部明确标记，保留原始数据供恢复，不虚构保存成功。

`timeslice` 触发间隔并不精确，计时应依据单调时钟和最终解码时长；持久化片段的机制依据 [MediaRecorder 文档](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/start)。

**验收。** 录音中强制关闭、磁盘写满、上传失败后重启，仍能恢复已落盘部分或给出明确恢复状态；录音中通过另一客户端改稿，旧录音仍引用开始时版本；重传两次不生成重复记录。

### F02：任务超时、故障恢复与调度完善

**缺口。** `jobs.py` 的 `WorkerBridge.invoke()` 使用阻塞 `stdout.readline()` 等待推理响应，没有看到请求级推理超时。已有取消可终止 worker，重启可将未完成任务标记失败，但尚无自动超时回收。0.2.1 文档记录过某输入 180 秒内未返回；这说明需要调查，不能直接认定缺少超时就是该次故障的原因。

**路线。** 为每次调用生成请求 ID，用专用读取线程消费响应，通过队列按 deadline 等待。分别记录进程启动、模型加载、推理、导出阶段耗时；超时后终止进程树、忽略旧响应并将任务标为可重试失败。失败信息同时给出“重试”和“选择轻量模型”等可执行操作。

先保留现有串行模型推理，增加耗时可观测性；再按测量结果考虑常驻 CPU TTS/ASR worker，并限制总内存。云端 HTTP/WebSocket 任务可放入独立的小并发队列，避免它们等待本地长推理。GPU 继续串行控制显存。不要在未测资源前默认让所有模型常驻。

**验收。** 模拟 worker 无响应和异常退出，任务在可配置期限内结束，下一任务可运行；取消与迟到响应不覆盖新任务；云端超时不阻塞本地播放；付费请求不因自动重试重复收费。

### F03：稿件库管理与导入

**缺口。** API 有会话新建、查询、进度和句子修改，没有会话标题修改、归档、搜索和删除路径；新建界面以粘贴文本为主。

**路线。**

- 会话增加 `updated_at`、`archived_at` 和可选标签，增加标题修改与归档接口。初期小数据量按标题筛选；记录增多后增加分页和索引，再评估 SQLite FTS5。
- 先支持 UTF-8 TXT/Markdown 文件预览导入，校验大小和编码，调用已有分句逻辑。PDF/DOCX 作为后续独立能力，不能把图片 PDF 当作可直接提取的文本。
- 删除区分归档与永久删除。永久删除前列出相关录音数量，处理进行中的任务，并在数据库事务内清理归属关系。
- 生成音频可能被多个句子或缓存引用，按引用关系清理，避免删除共享资产；文件删除失败进入待清理记录。

**验收。** 中文标题、同名稿件、空文件、超限文件、归档恢复均可处理；删除一个稿件不影响其他稿件或共享音频。

### F04：备份、恢复与磁盘管理

**缺口。** 已有 WAV 导出和数据目录配置，但未发现包含稿件、录音、反馈的备份/恢复流程。设置修改录音目录不会自动迁移既有记录中的绝对路径。

**路线。** 新增 `backup.py`，输出带版本的 ZIP：数据库快照、用户录音、必要元数据和文件哈希。模型权重和可重新生成的示范缓存默认排除，密钥不进入备份。数据库启用 WAL，采用 `sqlite3.Connection.backup()` 等快照机制；不能运行中只复制主数据库文件。[SQLite 备份机制](https://www.sqlite.org/backup.html)

备份期间冻结资产删除、迁移及相关写操作，保证数据库引用的文件集合一致。恢复先在临时目录验证版本、大小、哈希和解压路径，再建立新环境或执行明确的合并操作；按资产 ID 重建本机路径，不沿用另一电脑的绝对路径。录音目录迁移采用“复制 → 校验 → 事务改引用 → 保留原文件至确认完成”。

空间管理分别显示模型、用户录音、示范缓存、草稿和日志占用。默认只清理可重建缓存；用户录音需要明确选择。

**验收。** 备份到另一目录/电脑后可恢复稿件、录音和反馈；损坏 ZIP、非法路径、缺失文件被明确报告；中断迁移仍可访问原录音；清缓存不删除练习历史。

### F05：麦克风选择与录音预检

**缺口。** 当前 `getUserMedia({ audio: true })` 使用默认设备，波形已有真实信号，但尚未提供输入设备选择。后端质量观察在识别后以技术字段展示，不等于录音前可读诊断；保存时峰值限制也会影响事后观察削波。

**路线。** 用户授权后调用 `enumerateDevices()`，用 `deviceId` 选择输入；监听设备变更并处理耳机拔出。新增短录音试听，基于原始输入的 RMS、电平和持续近峰值比例提示“音量偏低”“可能过载”，阈值可配置并经设备验证。把故障提示连到 Windows 麦克风权限和设备设置说明。

原始输入的电平测量与保存后的归一化音频分开记录。短时音量不能证明环境噪声、清晰度或发音问题；不要自动给出“噪声严重”的确定结论。降噪如后续加入，应保存处理参数，并对 ASR 和发音评测分别验证影响。

**验收。** 多麦克风可切换，无设备、拒绝权限、设备被占用或断开均有恢复入口；安静录音与低音量录音提示有区别，正常设备不被持续误报。

### F06：整篇连续练习与声音对比

**缺口。** 已有整篇示范音频，但用户录音绑定单句，缺少整篇连续演讲的记录模型。单句示范循环和倍速已存在；还缺少“听示范 → 录一句 → 回听 → 下一句”的自动流程，以及指定片段的 A/B 切换。

**路线。** 分步发布，避免同时重写所有录音交互：

1. 先引入 `practice_attempt` 和整篇录音：保存有序句子 ID、各自版本、全文快照和录音资产，不通过挂在第一句来伪装整篇归属。
2. 录音时长上限按练习模式参数化，先设可控产品上限；增加流式落盘和音频分段处理，避免单次上传和内存随时长无界增长。
3. 本地 ASR 使用带上下文的分段，保存每段全局偏移，处理边界重复词。参考文本对齐用于回听定位，不把对齐成功当作发音正确。
4. 自动逐句练习用状态机 `listening → countdown → recording → saving → reviewing → next`；录音时暂停示范，避免扬声器音频进入麦克风。
5. A/B 对比先支持同一句的两个播放器快捷切换。局部示范位置使用可靠时间或明确用户选区，不照搬用户录音时间到时长不同的示范音频。

现有腾讯适配只实现句子模式。官方目前给句子模式限制 30 词/60 秒，段落 120 词/300 秒，自由说无需参考文本、最长 300 秒；它们是不同模式，必须新增请求/结果适配，不能只放宽前端限制。[腾讯模式说明](https://cloud.tencent.com/document/product/1774/107373)

**验收。** 多分钟录音保存和重启恢复正确；词时间采用全局坐标且不重复；自动流程可停止和重试；不把多个云端片段分数简单平均成整篇分。

### F07：转写校正、识别历史与练习报告

**缺口。** 后端已有 `recognition_history` 追加保存，前端主要展示最新 `content_feedback`，未发现识别历史选择与用户校正转写的完整流程。评测历史选择则已经实现。

**路线。** 前端增加转写历史选择与文本编辑；后端新增独立 `transcript_revision`，保存原始识别结果 ID、校正文本、修改时间及用户确认状态。校正只生成新版本，不覆盖供应商原始结果，也不擅自继承已经失效的词时间。插入或修改词的定位标为不可用，必要时重新对齐。

新增 Markdown/HTML 复盘导出，包含参考稿、用户确认转写、差异、供应商与模型版本、可靠片段位置和练习建议。初版不依赖 LLM；报告可作为 F09 的输入。

**验收。** 切换识别模型后仍能查看旧结果；校正记录与原始 ASR 都保留；校正一个重复词不错误映射到第一个同名词；无可靠定位时不出现可点击的虚假时间。

### F08：无稿回答与限时题卡

**缺口。** 当前会话以参考稿和句子为中心，不能直接表达“题目给定但答案开放”的任务。

**路线。** 增加 `practice_type`，初期包含 `read_aloud` 与 `free_response`；题卡保存题目、可选材料、准备时长、作答时长、规则版本。录音关联 `practice_attempt`；无稿回答先做转写、回听和同题重答，不调用参考稿编辑距离判断漏读。题库先使用原创或用户材料。

计时采用 deadline 和单调时钟，刷新/暂停行为明确。先交付通用限时练习；考试模式另核查当期官方规则并保存版本，不把此前文档中的计时直接视作当前规则。

**验收。** 同一题可保存多次回答；不存在范文仍能完成录音与回听；合理的不同表达不会被标为增词/漏词；计时结束与编码尾帧不会造成合法录音保存失败。

### F09：语言教练与“复盘后重答”

**缺口。** 当前模板提供一般音素知识，没有面向回答内容、语法、词汇和组织结构的语言分析服务。

**路线。** 新增独立 `LanguageCoachProvider` 和 `coach.py`，输入题目、用户确认的转写、练习目的和必要上下文；输出至多三条改进建议，每条包含原文引用、问题类别、修改示例和下一次可执行动作。初期选择一家支持结构化输出的服务，继续用户自带密钥；未来本地模型复用同一契约。

采用 JSON Schema/Pydantic 校验，核对引用是否存在、类别是否受支持、字段长度和版本；失败展示可重试状态。结构化输出帮助约束格式，但事实正确性和建议质量仍需验证。[百炼结构化输出说明](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

ASR 错误会传递给教练，因此 F07 是必要前置。文字模型只评文字内容，不凭转写推断音素、口型或自行生成音频时间；用户文本作为数据隔离处理。在线调用展示上传对象，记录实际 usage，失败不隐式换付费服务。

**验收。** 专门评估“建议是否引用真实原句”“是否改变原意”“是否能在下一次回答采用”；低可信转写先要求确认；不输出未经标定的考试分数。

### F10：韵律、重音和节奏能力

**缺口。** `feedback.py` 定义 `prosody`、`intelligibility`、`expressiveness`、`five_dimension_overall`，当前默认不可用；现有适配未产生完整可信来源。词间间隔也不是声学静音检测或韵律评分。

**路线分三层。**

1. **观察层：** 增加 VAD 语音区间、实际发声时长、停顿分布和有声段基频轨迹；所有观察附算法、阈值和适用条件。先基于现有 NumPy/SciPy 扩展，基频提取引擎通过小样本比较后确定。
2. **对比层：** 在可靠词/句定位下比较用户与示范的时长、停顿和相对音高变化；按说话人基频基线标准化，而非比较绝对音高。示范是练习参考，合理的不同语调不自动判错。
3. **评分层：** 只有获得人工标注、稳定供应商维度或经留出集验证的模型后才上线分数。不同供应商和模型版本保留来源，不拼接为未经验证的五维总分。

当前能做的是“这里出现较长停顿，建议回听”，不应直接升级为“这里流利度差”。可理解度尤其需要听者判断，不能由 ASR 成功率替代。

**验收。** 人工标注停顿与词时间做对照；覆盖合理停顿、疑问语调及不同音高说话人；报告定位误差和误报。若开发评分，训练/调参集与验收集按说话人隔离。

### F11：弱项收藏、练习计划与进步趋势

**缺口。** 有多次录音和评测历史，尚未形成跨稿件弱项管理、复习计划或学习趋势。

**路线。** 从用户主动收藏或确认的问题建立 `practice_item`，关联来源录音、词的出现位置、音素、原建议和状态。初期用透明规则安排复练，例如“今天、两天后、一周后”，用户可调整或移除；先不训练推荐模型。

趋势优先展示练习时长、复练完成率及同题重答次数。需要展示分数变化时，按同一供应商、模式、版本和相近条件分组，并注明样本量；不把不同量表合并画一条进步曲线。

**验收。** 一条未经用户确认的低分不会自动成为长期弱项；删除来源后计划不崩溃；跨供应商结果分开显示；用户可追溯每个练习项的来源。

### F12：首次使用、更新与支持工具

**缺口。** 模型设置已存在，但用户仍需理解模型、设备和 GPU 组件。Electron 当前负责启动后端、保存音频和选目录，未发现应用内版本检查与完整诊断导出流程；README 还包含 `OWNER` 发布链接占位。

**路线。** 首次向导只引导 CPU 基础路径：检查存储空间 → 准备模型 → 麦克风试听 → 完成一次练习。GPU 作为可选增强，提供组件版本和能力检测；检测到 NVIDIA 显卡不等于驱动、运行库和显存满足要求。

支持信息导出包括应用/组件版本、任务阶段耗时、硬件概况和脱敏日志，默认排除密钥、正文、录音和带令牌 URL；显示预览供用户检查。

更新先交付“检查新版本 → 查看说明 → 用户主动下载完整安装包”。以后保持 NSIS 时，应选与 NSIS 匹配的更新方案并核查文档；不能直接假设 Electron 内置 `autoUpdater` 适用于当前安装目标，其官方 Windows 路径涉及 Squirrel.Windows/MSIX。[Electron 更新文档](https://www.electronjs.org/docs/latest/api/auto-updater)

升级安装应验证旧数据副本、数据库版本和回退边界；公开发布地址、安装包签名和第三方许可材料单独补齐。

**验收。** 新用户在无开发环境的 Windows 上完成 CPU 首次练习；断网可使用已准备模型；诊断包没有凭据和私人音频；升级后历史仍可访问。

## 5. 推荐开发顺序与依赖

不建议一次同时交付以上所有功能。每个阶段可拆成多个独立版本，分别验收。

| 阶段 | 建议顺序 | 交付后的用户能力 | 主要依赖 |
|---|---|---|---|
| A：可靠基础 | F02 → F01 | 任务能失败退出，录音能恢复且归属正确 | 现有任务队列、Electron、版本快照 |
| B：日常可用 | F03、F04、F05、F12 的首次使用部分，逐项发布 | 能管理材料、迁移数据并独立开始练习 | 事务和资产关系、真实设备验收 |
| C：完整练习 | F06 的整篇录音 → F07 → F06 的自动流程/A-B | 从单句扩展到整篇，能校正并导出复盘 | 草稿恢复、练习记录模型 |
| D：开放表达 | F08 → F09 | 限时回答、复盘建议、同题重答 | 练习类型、用户确认转写 |
| E：持续训练 | F11 → F10，更新机制择需发布 | 弱项复练和有依据的声音观察 | 稳定历史、人工标注和使用反馈 |

S/M/L 表示相对实现复杂度，不是工期估算；真人样本、真实云端账号、低配置设备和发布资源会影响交付时间。

## 6. 数据与模块设计建议

保持 Electron + React/TypeScript + FastAPI + SQLite，按业务边界增加模块。先扩展当前通用对象存储；出现明确的查询性能需求后再增加关系表或派生索引，避免先迁移全部历史。

建议新增或扩展对象：

| 对象 | 关键字段 | 用途 |
|---|---|---|
| `practice_attempt` | 类型、会话/题目 ID、参考快照、规则版本、开始/结束时间、状态 | 统一单句、整篇和无稿回答的练习归属 |
| `recording_draft` | 草稿 ID、attempt ID、片段序号、完整性、落盘状态 | 崩溃恢复、重传和去重 |
| `transcript_revision` | 原始 ASR ID、文本、确认状态、修改时间 | 区分模型输出和用户校正 |
| `coach_result` | 转写版本、服务/模型版本、建议、usage、状态 | 可追溯语言复盘 |
| `practice_item` | 来源、出现位置、用户确认、下次复练时间、状态 | 可解释的弱项训练 |
| `backup_manifest` | 格式版本、资产相对路径、大小、哈希 | 跨目录迁移与恢复 |

几个必要不变量：

1. 录音、识别、评测和教练建议都能定位到对应练习及当时的文本版本。
2. 原始供应商结果保留，用户校正和应用解释另存，不覆盖原始证据。
3. 没有可靠时间就不提供精确回放定位；不同音频不能共用未经验证的时间轴。
4. 任务失败、取消和迟到响应不会覆盖新结果或复活已删除数据。
5. 备份和删除同时处理数据库引用与文件，生成缓存按引用清理。

## 7. 已有功能需要补验收的项目

这些事项不应写成“功能没做”，但会决定软件是否适合进一步发布：

| 项目 | 当前证据限制 | 下一步验证 |
|---|---|---|
| 真人识别与差异误报 | 有限真人录音无独立人工转写真值；大量流程使用合成语音 | 先建立至少 30 条、3 名说话人的人工转写集，再扩大；以说话人划分调参与验收 |
| 云端评测 | 官方样例和模拟协议验证不能证明真实账号可用 | 使用有权限账号验证成功、权限/额度错误、超时、费用和实际音素定位 |
| 纠音建议有效性 | 通用音素模板没有证明能诊断个体原因 | 人工听辨反馈和复练前后对照，分别检查错误定位与建议可执行性 |
| TTS 质量与等待 | 有真实生成，缺乏人工盲听；0.6B 曾存在超时输入 | 固定材料记录冷/热等待、失败率，人工检查增词、漏读和听感 |
| 安装与硬件 | 开发机冻结流程不等于干净普通电脑 | 无 Python/Node 的 Windows 11、较低配置 CPU、物理麦克风与断网验收 |
| 公开发行 | 未签名、公开链接占位、部分许可/依赖审查未完成 | 验证真实发布地址、签名、对应源码与第三方材料、升级后的数据兼容 |

算法验证必须区分两个参考对象：**人工转写**用于计算 ASR 的 WER，**意图稿件**用于判断练习内容差异。用户真的漏读一个词时，ASR 正确识别漏读不算识别错误。`WER=(替换+删除+插入)/人工转写词数`，它也不是发音质量评分。

## 8. 下一轮可执行建议

建议首先单独交付 **F02：任务超时与明确重试**：它直接利用现有队列，范围可控，同时为后续长录音、语言教练和云端任务提供基础。先复现无响应/退出边界，记录请求阶段和耗时，加入可配置 deadline 与 worker 回收，再验收下一任务能正常执行。

随后交付 **F01：持久录音草稿与开始时版本快照**，优先保护用户已经完成的练习。完成这两项后，再按实际用户使用反馈选择稿件管理、备份或整篇连续录音。

以上路线不要求先更换默认 ASR 或训练新模型。当前阶段，完善录音归属、恢复和反馈来源，比增加一个未经本项目数据验证的模型更能形成可验收的产品收益。
